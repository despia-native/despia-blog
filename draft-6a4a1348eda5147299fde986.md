---
title: "In-App Purchases Without a Backend: Despia + RevenueCat"

---

The moment you wire real billing into a hand-built paywall, you end up with two records of who is subscribed: a flag in your app and an entitlement in RevenueCat. Builders reach for a webhook into their mobile runtime to keep the two in step. In a Despia app there is no such webhook, and for most apps there does not need to be. One of those two records is authoritative, and your app can read it straight off the device.

## Two systems tracking one fact

When you build a paywall by hand, the tier is usually a boolean you set yourself: `isPremium = true`. That value is a guess. Your UI writes it, not the store, so nothing outside your app agrees with it.

Add RevenueCat and now the same fact lives in two places. Your flag, and the entitlement RevenueCat derives from the actual receipt. They agree right up until the first renewal, lapse, or refund, because only one of them hears about those events. The other keeps lying.

The reflex is to make them talk: a webhook, a synced table, both kept in step. That reflex has the problem right and the fix wrong. You do not reconcile two sources of truth. You delete one and read the other.

## RevenueCat is the backend, Despia is the runtime

Keep the roles straight and the whole thing collapses to something simple.

RevenueCat is the source of truth for who is subscribed. It talks to StoreKit on iOS and Play Billing on Android, records every purchase, renewal, and cancellation, and resolves it all into entitlements like `premium` or `no_ads` that read identically on both platforms. That is a backend job, and it is already done.

Despia is the native runtime. It ships your web app as a real iOS and Android binary and exposes that native billing to your JavaScript through `despia()`. It launches paywalls, takes purchases, and returns purchase history. It does not store subscription state and it is not a thing you point a backend at. It is your frontend, running natively.

So "is there a webhook in the runtime to sync my subscriptions" has no target. There is nothing in the runtime to sync. The state lives in RevenueCat, and the job is to read it, not mirror it.

## The whole flow, on device

Enable RevenueCat under Despia > App > Settings > Integrations and drop in your API key. Then it is two functions.

Launch the native paywall, with a web fallback so the same code path works outside the app:

```javascript
const isDespia = navigator.userAgent.toLowerCase().includes('despia')

function buyPremium(userId) {
  if (isDespia) {
    despia(`revenuecat://launchPaywall?external_id=${userId}&offering=default`)
  } else {
    // web pays through a RevenueCat link tied to the same user id
    window.location.href = `https://pay.rev.cat/<token>/${encodeURIComponent(userId)}`
  }
}
```

Then read entitlements. One function, reused everywhere the state can change:

```javascript
async function checkEntitlements() {
  const data = await despia('getpurchasehistory://', ['restoredData'])
  const active = (data.restoredData ?? []).filter(p => p.isActive)
  if (active.some(p => p.entitlementId === 'premium')) unlockPremium()
}

checkEntitlements()                              // on load
window.onRevenueCatPurchase = checkEntitlements  // and after every purchase
```

Two things worth knowing here, because they are where people trip.

`onRevenueCatPurchase` fires when a purchase succeeds on the client, but it is a signal, not a grant. Do not unlock straight from it. Use it as the cue to re-run the entitlement check, so access is always gated on what RevenueCat actually reports, never on the fact that a tap happened.

Gate on the `entitlementId`, not on the product. Set the entitlement up once in RevenueCat and attach both your iOS and Android products to it, and both platforms return the same id. Your tier logic stops caring which store the user came from. If you call `revenuecat://purchase` directly instead of a paywall, note the product string differs per platform (Android carries the base plan, as in `premium:monthly_premium_android`), which is exactly the kind of detail a shared entitlement lets you stop hand-managing.

Run the check in three places: on load, on navigation, and before you gate a premium action. The calls are instant and work offline, because Apple and Google cache entitlement state on the device. No server round trip, no second database, and it survives reinstalls because a restore pulls the same entitlements back.

## The one caveat: web purchases are invisible to the device check

`getpurchasehistory://` only sees native App Store and Play purchases. If a user paid through the web link, the on-device check will not show it. If you sell on both web and native, check your backend first and treat the native check as the fallback. For an app that only sells inside the stores, the device check is the entire story.

## "None of the products registered in the RevenueCat dashboard could be fetched from App Store Connect"

This is the error that sends people hunting for a code or backend fix, and it is neither. Your product ids can be correct in RevenueCat and App Store Connect, your API key valid, your build fine, and you still get an empty product list.

The cause is upstream at Apple. App Store Connect will not release products for sale until Agreements, Tax, and Banking is complete and approved. Until then your app asks Apple for the product list and Apple hands back nothing, which surfaces as a configuration error. It applies in TestFlight too. Apple blocks every purchase, including test ones, until that section clears.

The fix never touches your app:

1.  Open App Store Connect, go to Agreements, Tax, and Banking.
    
2.  Accept the Paid Applications Agreement if it is not active.
    
3.  Add your banking details.
    
4.  Submit your tax forms.
    
5.  Wait one to two days for Apple to approve all three.
    

Once approved, products load on their own, no rebuild.

## When you do want a backend, it probably is not a webhook

The device check gates the UI. It protects nothing on a server. The moment a user faking client state could take something you cannot claw back, a premium API call, a server-delivered file, tokens on your own bill, the gate has to move server-side. That is a real need, and it still is not a reason to run webhooks.

Here is the pattern that skips them. The client already knows the app user id it handed RevenueCat. Send that id to your backend, and have the backend ask RevenueCat whether the user is entitled, right before it does the expensive thing.

```javascript
// server-side only, the secret key never touches the client
async function isSubscribed(appUserId) {
  const uid = encodeURIComponent(appUserId) // anon ids carry a $RCAnonymousID: prefix
  const res = await fetch(
    `https://api.revenuecat.com/v2/projects/${PROJECT_ID}/customers/${uid}/active_entitlements`,
    { headers: { Authorization: `Bearer ${RC_SECRET_KEY}` } }
  )
  const { items } = await res.json()
  return items.some(e => e.entitlement_id === 'premium')
}
```

Then gate the route:

```javascript
// inside the AI proxy, or any subscriber-only endpoint
if (!(await isSubscribed(userId))) {
  return new Response('subscription required', { status: 402 })
}
// safe to call the model and return the result
```

This fits the app you are probably building. Almost every utility app now ships an AI feature, which means it already runs a backend to proxy the model call and keep the key off the client. That proxy is exactly where the subscription gate belongs, and it answers the question with one call to RevenueCat instead of a webhook pipeline and a mirrored table you have to keep correct.

A few specifics so it works the first time. The endpoint is keyed by the app user id and needs your RevenueCat secret key, so it only ever runs on the server. It returns a list of active entitlements, each carrying an `entitlement_id` and an `expires_at` in epoch milliseconds (null for lifetime), and nothing about which product or plan produced it. Most customers fit one page. If `next_page` comes back non-null, follow it until it is null. One gotcha while testing: sandbox and simulated StoreKit grants sometimes return an empty list even when the entitlement is clearly active, so cross-check the v1 `/subscribers/{app_user_id}` endpoint before concluding it is missing.

Webhooks still have their place. When you need the change the instant it happens, a downgrade that must cut access on the same second, a cancellation that fires a lifecycle email, an analytics event, that is event-driven work a synchronous check cannot do. But that is an optimization you add once you have paying users, not a thing to debug before your first one. Start with the direct gate. Add the webhook when a feature actually demands real-time.

The line that decides all of it: gate the UI on the device, gate anything valuable on the server, and let RevenueCat be the single thing both of them ask. The webhook comes in only when a second of delay is a second too many.
